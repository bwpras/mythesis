## Bug found and fixed (real data)

**Symptom:** running Stage 1 against real `data/raw/Dati01` crashed all 8 GPS/PJM file reads with `OSError`.

**Root cause:** `read_pjm_file39`'s 38B/39B format disambiguation speculatively decodes 8 arbitrary bytes as a posix-ms timestamp and only accepts that interpretation if it falls in a plausible range (2025–2030); otherwise it re-reads as the other format. MATLAB's `datetime()` silently produces an out-of-range value for implausible input and lets the plausibility check reject it. Python's `datetime.fromtimestamp()` instead raises `OSError` on Windows once the value is far enough out of range — observed on a real byte sequence that decoded to ~year 16149 (raw = 447743057664036 ms).

**Fix:** `_posix_ms_to_datetime()` in `python_port/ingestion/read_pjm_file.py` now catches `OSError`/`OverflowError`/`ValueError` and returns a sentinel date past the valid window, so the existing plausibility check rejects it exactly as MATLAB's does. Re-ran on real data: all 8 GPS files parsed correctly afterward, producing plausible coordinates (44.897°N, consistent with the repo's Northern Italy rail context).

**Regression test added:** `test_pjm_reader_survives_out_of_range_speculative_timestamp` in `python_port/tests/test_ingestion_smoke.py`, using the literal byte value that crashed on real data.
