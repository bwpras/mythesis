# Unresolved issues

- `Collect_Healthy_SensorData` requires data-backed verification of its expected BC/WV roster.
- The `Nodo` input schema is implicit and lacks a formal validator.
- ~~Sensor-label provenance (MBP/BC/WV) is inconsistent and undocumented.~~ Fixed: `loadNodoData.m`'s `LabelDirectory()` (and the Python port's `_label_directory()`) previously computed `<parent of rootDir>/label_registry` (e.g. `data/raw/label_registry`), silently ignoring the pre-existing `data/interim/label_registry` cache and re-classifying sensors from scratch on every run against a new raw folder. Both now resolve to the canonical, project-root-relative `data/interim/label_registry`, independent of `rootDir`. Format interop is now one-directional: the Python port reads MATLAB's `.mat` table cache directly when no `.csv` cache exists yet (`python_port/ingestion/mat_table_reader.py`, reverse-engineered against all 14 real registry files, no MATLAB needed), so it reuses labels MATLAB already classified. MATLAB itself still cannot read the port's `.csv` cache — closing that direction would require changing `loadNodoData.m`'s `ReadLabel()` too.
- Several workflows still require manual GUI selection by design.
- Active MATLAB scripts retain `clear`, `close all`, and `clc`; changing them could alter interactive behavior.
- `Algorithm_main.m` uses `eval(sprintf(...))`; it was preserved to avoid behavior change.
- Active batch and interactive scripts use different braking detectors.
- Historical algorithm and notebook variants may contain useful but unvalidated logic.
- No automated MATLAB or Python tests were found.
- Notebook outputs retain historical machine-local Jupyter temp paths.
- Required reference `model.csv` and named operational feature CSVs were not found during static inspection. `model.csv` has since been supplied by the user directly into `data/external/`. The named operational feature CSVs (`TestBrakefinal_data_raw_DatiXX.csv`) are now producible via the Python port — see the `detect_subphases_sets.m` entry below — but MATLAB itself still cannot produce them (its own CSV-writing call remains commented out).
- "No automated MATLAB or Python tests were found" (above) is now stale for Stage 1 specifically: `python_port/tests/` has 8 passing self-tests (`python python_port/tests/test_ingestion_smoke.py`). Still true for MATLAB — no `.m` tests exist for `loadNodoData.m`/`batchprocess.m`/`identify_brake_sensors.m`.
- `batchprocess.m` still has a hardcoded `tMin`/`tMax` date window (lines 66–67, currently 2026-01-01 to 2026-02-18) that must be edited in source to change; its inline comment ("one-month window: [1 Dec, 31 Dec)") no longer matches those dates either. The Python port already exposes this as `--start-date`/`--end-date` CLI flags — the MATLAB side wasn't changed to match.
- The Python port's Stage 1 has never been numerically cross-checked against real MATLAB output (Tier 2 validation in `python_port/README.md`) — there's no MATLAB installation in this environment to produce a reference file against. Confirmed so far: internal self-consistency (synthetic tests) and that it runs end-to-end against real `data/raw/DatiXX` `.bin` files without crashing — not that its numbers agree with MATLAB's.
- `python_port/ingestion/mat_table_reader.py` decodes MATLAB's undocumented, internal MCOS binary object format (not a documented file format) to read `label_registry/*.mat` tables. Verified against all 14 real registry files currently in this repo; would need re-verification if a differently-versioned MATLAB ever writes those files (it does fail loudly with `ValueError` on a schema mismatch rather than silently misreading, but that's a narrower guarantee than "known to work across MATLAB versions").
- Sensor-role classification thresholds (`identify_brake_sensors.m`/`.py`: MBP > 4.6 bar, BC < 0.2 bar, else WV, over a steady-window median) are fixed heuristic cutoffs, not validated against a broader sensor population — related to, but distinct from, the `Collect_Healthy_SensorData` roster issue above (that one's about Stage 2's healthy-sensor list; this is about the Stage 1 classifier itself).
- ~~`matlab/feature_extraction/pick_reference_phase.m` checks a struct field named `'BrakingAct'`...~~ Fixed in the Python port (`python_port/feature_extraction/pick_reference_phase.py`), documented as a deviation. Correction to an earlier (wrong) diagnosis of this same issue: `'BrakingAct'` is `count_valid_streams()`'s *optional* field argument, not the required one (`'SensorError'` is required, and works correctly) — the function's own logic defaults `optOK = true` whenever the optional field is absent, so the effect is the opposite of "refPhase always NaN": BC validity silently only requires `SensorError==0`, ignoring the intended `NormalBraking==1` condition entirely (a *weaker* filter than documented, not a maximally strict/always-failing one). Confirmed as a stale rename (not intentional): `Collect_Healthy_SensorData.m`'s own docstring uses the identical stale `"BrakingAct==1"` wording while its actual code already correctly reads `.NormalBraking`. The Python port maps the optional-field name to `'NormalBraking'`, matching that file's real behavior.
- `matlab/main/Algorithm_main_batch.m` (the active batch entry point) calls `detect_subphases_sets(...)`, but that function does not exist anywhere in the active `matlab/` tree — only two functionally-identical copies exist under `archive/matlab_legacy/` (`algorithm_experiment_backup/` and `algorithm_feature_extraction_outer/`). Running the active MATLAB batch pipeline today would fail with an undefined-function error at that call. **The Python port is unaffected and complete**: `python_port/feature_extraction/detect_subphases_sets.py` is ported against the archived copy's logic as ground truth, and Stage 2 of the Python port (`Nodo` -> `TestBrake` -> pairing -> subphase detection -> post-processing -> CSV) is now done end to end via `python_port/feature_extraction/pipeline.py`. The MATLAB source itself still hasn't been repaired (out of scope for a Python port; would need the file copied back into `matlab/feature_extraction/` to fix MATLAB-side execution) — same for MATLAB's separate, still-commented-out CSV-writing call (`update_brake_master.m` in `Algorithm_main_batch.m`), which the Python port closes with new functionality rather than a line-by-line port (see `python_port/feature_extraction/csv_export.py`).
- The Python port's Stage 2 has never been numerically cross-checked against real MATLAB output — same caveat as Stage 1's Tier 2 (no MATLAB installation in this environment). Confirmed so far: 36 passing synthetic self-tests (`python python_port/tests/test_feature_extraction_smoke.py`), a 109-field whitelist (`KEEP_FIELDS`) cross-checked programmatically against the literal MATLAB source (exact match), and an end-to-end run against real Dati01 hardware data producing a 132-row CSV with plausible derived-field values — not that those values numerically agree with what real MATLAB would compute for the same input.
